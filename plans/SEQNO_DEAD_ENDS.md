# 序號計數器:四條走過的死路

狀態:程式碼已移除(gfxstream),這份文件是它存在過的理由。2026-08-05。

## 問題長什麼樣

gfxstream 的每個 Vulkan 封包帶一個序號,host 解碼前要等該客體行程的計數器追上
(`want = have + 1`)。計數器在每個 opcode 的 epilogue 遞增。任何一個「讀了序號但沒跑到 epilogue」
的路徑——沒有 case 的 opcode、提早 return、執行緒中途結束——都會讓計數器永遠少一,
**該行程的每一條執行緒從此永遠等下去**。

實測過的樣子:`want=10352 have=10350`,幾分鐘不動,kwin 的 render thread 全部停在那裡,桌面不畫。

## 四條死路

都試過,都有各自的副作用,所以最後**一條都沒留**:

| # | 做法 | 結果 |
|---|---|---|
| 1 | `delta <= 0` 就直接 break(看到不對就放行) | 該行程的順序保證整個消失,KDE 合成黑畫面 |
| 2 | 一看到計數器超前就 rewind 到這個封包的編號 | **打死 VM**——其他執行緒早就走過那個編號了 |
| 3 | 停滯數秒後再 rewind | 一樣**打死 VM**,只是慢一點 |
| 4 | 只往前不往後(`store(seqno-1)`),且停滯數秒後才做 | VM 活著,但桌面不畫 |

第 2、3 條的教訓最重要:**計數器是共享的,倒退它等於對所有還在跑的執行緒說謊。**

## 為什麼最後選擇不修

因為「計數器掉一格」是**症狀不是病因**。真正的缺口是封包在傳輸中遺失,或某個 opcode 的
客體/主機長度不一致——修計數器是在對帳本動手腳而不是找出少掉的那筆錢。

而且不變式散在 383 個 epilogue 裡,任何一個新增的提早 return 都會再製造一次。要真的解決,
得讓「讀序號」和「遞增序號」在結構上不可分離(例如 RAII),而不是加補丁。
(試過 `SeqnoFloor` RAII 守衛,但它對「讀了卻沒解碼」的封包也會觸發,造成 `want=2 have=2` 的重試死鎖。)

## 留下來的

上游行為:等,而且一直等。加上兩個診斷——自旋數到達病態門檻時報一次
(`GFXSTREAM_DIAG=1`,4096 圈起),以及不設開關的「這個等待已經不是等待了」單行警告(2^22 圈)。
