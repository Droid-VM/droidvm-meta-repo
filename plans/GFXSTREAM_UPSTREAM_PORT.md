# gfxstream 升上游 + 重新移植計畫（2026-08-21）

範圍：`gfxstream` 一個 repo 的 `wip/3d-accel`（103 commits，淨 12,624 行 / 68 檔），
連帶 `mesa` `wip/3d-accel` 的 host-compat shim 與 `crosvm` 的三處 ABI。

**動機**：guest mesa 已經跟到 main（26.3.0-devel），它的 gfxstream encoder 大幅前進；
host 還停在 2025-09 的 AOSP snapshot，只能靠手工補 cereal 表去接。與其繼續爆改 host，
不如把 host 升到上游，讓兩邊天然對齊，本地只留 **pVM port** 和 **真 bug fix**。

**已定的三個決定**
1. 目標分支 **`aosp/emu-main-dev`**（2026-08-11，gfxstream 開發主線）。
2. 診斷收斂成 **單一 `GFXSTREAM_DIAG` 開關**；`DecoderProfile`（~700 行）**丟**。
3. **AHB 那批（X3）不移植** — 證據見 §4。

## 2. 為什麼是「重新移植」而不是 rebase

1. **沒有共同祖先**：clone 是 shallow，graft 在 `7e9d595b0`，`git merge-base HEAD aosp/emu-main-dev` 回空。
2. **上游做過全樹改名**：`host/` 下的 C++ 全部 CamelCase → snake_case，`host/backend/` → `host/common/`，
   整個 host 塞進 `namespace gfxstream::host`。逐檔改名 + 我們動過的兩個大檔各被上游改了近 3,000 行
   （`vk_decoder_global_state.cpp` 2,980、`vk_common_operations.cpp` 2,696），rebase 只會產出無法審的衝突。

→ **做法**：從 `aosp/emu-main-dev` 開新分支，按 bucket 把改動重寫上去。
這跟 `plans/PR_FLATTEN_PLAN.md` 的 gfxstream 扁平化（95 → 22）是**同一件事**，一次做完。

## 3. 升上游省下什麼（實測，非推測）

拿 repo 自己那支 `scripts/check-cereal-compat.py`，對同一份 mesa 26.3 guest encoder 跑兩個 host：

```
現在的 host（VK 313 + 3,474 行手工 splice）
  guest encoder can send 212 pNext structs
  → 全覆蓋，但需隱藏 11 個 struct（maintenance9 / robustness2 / setMetadata / Android-only）

上游 emu-main-dev（VK 350，原封不動）
  guest encoder can send 212 pNext structs
  → host decoder covers everything.   需隱藏 0 個
```

capset 也天然對齊 —— 我們手工補的那格 padding，上游本來就有：

```c
/* aosp/emu-main-dev host/virtgpu_gfxstream_protocol.h */
    uint32_t hasTraceAsyncCommand;
    uint32_t hasSetMetadataCommand;   // ← 我們手工補的「keep offsets aligned」
```

上游還自帶了幾件我們也碰過的事：`DeviceOpBuilder::OnQueueSubmissionAborted`（對應 `a3fb53d7a`）、
`type1Read` 對 guest 可控 offset/size 的驗證、ASG snapshot、`mLinear` 過小時的明確錯誤而非 nullptr deref。

**soong 建置面風險低**：比對全部 `Android.bp`，上游**沒有新增任何 gfxstream 以外的外部相依**
（37 → 36 個），`libgfxstream_backend` 仍在——crosvm 只引用這一個模組，內部模組改名
（`libgfxstream_host_backend` → `_host_common`、`_host_health`/`_metrics` 消失）不影響 crosvm。

## 4. AHB 那批為什麼不移植

`5_prepare_turnip.sh` 自己寫得很清楚：

> 沒有 turnip，gfxstream 會退回手機的閉源 Adreno blob（AHB-only, `supportsDmaBuf=0`）
> → host-visible coherent memory 失敗（"dmabuf not supported"）→ zink/desktop 黑畫面。

也就是說 **AHB 路線在 pVM host-visible 設計下本來就走不通**（整個 GpuPool / folio / guest-alloc
都建立在 dma-buf 上）。X3 那 5 個 commit（`87a26ce3e` dedicated export、`d30f31837` convergence query、
`62b2f9170` BGRA8→RGBA8、`01d07a5a4` stride fallback、`2c57c465f` `AHardwareBuffer_lock`）服務的是
一條我們不支援、也不可能支援的路線。**丟。**

同批裡**不是** AHB 的三個要個別處理：

| commit | 內容 | 處置 |
|---|---|---|
| `1c6e27ef3` | `on_vkGetImageMemoryRequirements` 對非壓縮格式提早 return，害 guest 拿到未映射的 memoryTypeBits（maintenance4 路徑壞掉） | **移植**（真 bug，與 AHB 無關） |
| `f038bd111` | blob 資源跳過 `AttachIov` → `mLinear` 是 nullptr → scanout 的 `transfer_read` SIGSEGV | **移植，但要改寫**：上游已加 `mLinear.size() < requiredSize` 的錯誤回傳，我們要的是**延遲配置**而不是報錯 |
| `e1d0472b5` | 把 `VkPhysicalDeviceVulkan13Features` 全部欄位歸零（Adreno 750 閉源 blob 會拒絕非零欄位） | **待驗**：目前是**無條件**執行，等於在 turnip 上也把所有 1.3 feature 關掉。turnip 路線大機率不需要，落地前要在機器上驗 |

`0c2064df5`(tmp) / `166a754aa`(wip) / `364cb8d9e` / `85d737cba` 是同批的基礎工（loader 解析、turnip
dma-buf export、`createBlob` iovec），其中 dma-buf export 的部分要先比對上游——上游已有 `supportsDmaBuf`
的完整 plumbing（`vk_common_operations.cpp:1190/1434/2192/2506/4890`），我們的版本可能大半已經不需要。

## 8. 待驗清單

每個標「待驗」的 bucket，落地前先在上游樹上 grep 對應症狀，已修就丟：

- X1/X2：上游 Android 分支的 `getMemoryHandleFunc` 選擇邏輯（`vk_common_operations.cpp` ~1600 行附近）
- X9：`a3fb53d7a` 上游已有 `OnQueueSubmissionAborted`，其餘四個要逐一比
- X16：上游 `ring_stream.cpp` 已加 guest 可控 offset/size 驗證與 snapshot；framing 修復可能大半不需要
- X19：上游 teardown 路徑是否已經不再跨 context id
- `e1d0472b5`：turnip 路線是否真的需要把 Vulkan 1.3 features 歸零（**風險最高的一個**，目前無條件執行）

## 9. 風險

1. **量測基準全部作廢**：X14/X15 的數字（vkmark 4129→8713）是在舊 host 上量的，上游兩個大檔各動了近 3,000 行，
   落地後要重新量，不能假設效果一樣。
2. **`e1d0472b5` 無條件關掉 1.3 features**：升上游後 guest zink 能拿到的 feature 集合會變，這條要優先驗。
3. **pool 的環境變數介面**（`GFXSTREAM_POOL_FD` 等四個）是我們自訂的，上游無關，但 X6 落地時要確認上游
   `vkAllocateMemory` 的結構改動不影響 pool 的插入點。
4. **force-push**：新分支會取代 `Droid-VM/gfxstream` 的 `wip/3d-accel`，備份分支必須先推上去。

### 移植過程中額外發現

1. **`RingBlob::CreateWithExternalMemory` 是死碼**：只服務「guest 用 iovec 提供 ring 頁面」那條
   分支，但 guest 的 ASG ring 一律以 `kBlobMemHost3d` 建立（mesa

2. **pool-resident ring blob 的 snapshot 會靜默損毀**：舊樹存成 `TYPE_HOST_MEMORY`，restore 後

3. **`UdmabufCreator::handleFromFd` 缺 stub 實作**：舊樹只改 `_linux.cpp`，非 Linux 連結會失敗。

5. **X8 的三個洩漏上游都還在**；但上游把 export 收斂成 `fillExportHandle`，Android dup 修正
   只需改一處。
6. **capset 逐欄位比對**：guest 與 host 兩份 `vulkanCapset` 現在 15 個欄位完全一致。
7. **`check-cereal-compat.py` 對移植樹實測**：212 個 pNext struct 全覆蓋、零隱藏。

8. **上游 `ExternalMemory::calculateMode()` 在 `__ANDROID__` 只列 `AndroidAHB`**，沒有 fd 退路。
   照預設走，host 會宣告一種它沒辦法分享的 external memory，guest 渲染進沒人 scanout 的頁 →
   黑畫面且兩邊都不報錯。已顯式選 `OpaqueFd`（有 `VK_EXT_external_memory_dma_buf` 時自動升級成
   `DMA_BUF_BIT_EXT`）。這是移植後在裝置上會直接壞掉、但純看舊 commit 看不出來的點。
9. **上游 `cleanupProcGLObjects` 會無界等待**同 puid 的 render thread。guest 會回收 context id，
   等到的是「接手者」的執行緒——活著、正在服務、沒有理由結束 → cleanup worker 永不返回。
10. **上游 `on_vkResetFences` 的自旋**用「掃描 tracker」當退出條件，而掃描就是問 driver 的地方，
    整段還在全域鎖內。退出條件是它自己的副作用。
11. **`vk_emulated_physical_device_memory` 的 11 個上游單元測試**在移植後全數通過。

### R↔B 通道對調：根因已定位（08-22），修正待驗

畫面正常、kwin 零錯誤、guest 開到桌面，但顏色 R 和 B 對調。

**先更正上一版寫在這裡的因果鏈——方向是反的。** 上一版寫「fourcc AB24 → AR24、crosvm 不再交換」，實測是**反過來**：舊 AR24、新 AB24，crosvm 是**開始**交換。當時只有新 .so 的單一觀測就去推變化，沒有對照組。

實測（8gen3 / 5567，只換 `.so`，其餘全部相同）：

| | 進 crosvm 的原始位元組（swizzle 前） | kwin 的三顆 scanout fb | 畫面左上 |
|---|---|---|---|
| 舊 `.so` | `67 7d 57 ff  6a 80 5b ff …` | AR24 ×3 | `95 b0 9f` ✅ |
| 新 `.so` | **逐 byte 相同** | AB24 ×3 | `9f b0 95` ❌ |
| 新 `.so` + `NO_SWIZZLE=1` | 逐 byte 相同 | AB24 ×3 | `95 b0 9f` ✅ |

`framebuffer` 那一欄是 guest 核心自己記的（`/sys/kernel/debug/dri/0/framebuffer`），完全不經過 host。

**結論：畫素內容從頭到尾是 B-first、一個 bit 沒變，變的是 guest 貼上去的標籤。** crosvm 照著 fourcc 辦事，做的是對的事，只是被錯的宣告指揮。

真正的根因是**兩個漏移植的本地修正**（不是任何一顆新 commit 的 regression）：

**(1) host 沒再把 `VK_EXT_image_drm_format_modifier` 藏起來**（`kHiddenDeviceExtensions` 整段沒移植過來）。host 的 Qualcomm driver 只暴露一個 QCOM-tiled modifier、只給 BGRA8、且拒絕 `COLOR_ATTACHMENT`；compositor 只收 LINEAR/INVALID——兩個集合不相交。藏起來，guest ICD 才會走 LINEAR 模擬路徑（`gfxstream_vk_physical_device_init()`：host 沒有這個 extension → `doImageDrmFormatModifierEmulation = true`）。

**這一半和 guest 的 zink patch `4991af2cff6` 是配對的**——那顆 commit 的前提原句就是「the host hides it deliberately and the guest ICD emulates it LINEAR-only」。移植了 guest 那半、漏了 host 這半，樹是內部不一致的。

**(2) `on_vkGetPhysicalDeviceFormatProperties` 的 `gfxstream-zerocopy` strip 沒移植**：把 guest `getVirglFormat()` 匯不出去的格式（`R16G16B16A16_{SFLOAT,UNORM}`、`A2B10G10R10`、`A2R10G10B10`）的 `COLOR_ATTACHMENT` 位元清掉。這是 vkmark 那條的原因，見下。

補回時的兩點差異，都是刻意的：

- **只藏 modifier 一個。** 舊樹也藏 `VK_KHR_maintenance9` / `VK_KHR_robustness2`，但那是因為舊 cereal 解不了它們的結構——升級正好消滅那個限制，guest 端對應的隱藏（`c08fd270f69`）也已經拿掉，所以那兩個保持可見
- **strip 放 v1 + v2 兩條。** 舊樹只放 v1；補回 alias 之後 v2 才真的通到 driver，只補 v1 等於留一顆下次會再爆的雷
- 新樹多一個舊樹沒有的 `shouldPassthrough` 早退路徑（直接回傳 driver 原始清單），會繞過所有過濾，一併擋掉

**為什麼這不是「讓 host 少報」**：砍 `COLOR_ATTACHMENT_BIT`、藏掉一個協商不起來的 extension，回報的是**這套堆疊**的真實能力，不是隱瞞 driver 的能力。一個 `getVirglFormat()` 匯不出 virtio-gpu resource 的格式，在這條路徑上本來就不能當 scanout/dmabuf 目標——回報它可用才是說謊。跟「用一個謊抵銷另一個謊」的差別在於：後者換一台機器就不成立，前者在哪台機器上都成立。

`GPU_POOL_SCANOUT_NO_SWIZZLE=1` **只能當證據不能出貨**——它是全域 kill-switch，關掉會打壞 drm2kgsl 和 fbcon（那兩條是真的宣告 ABGR、內容真的是 R-first，需要那個交換）。

修正版的驗收標準（三個獨立指標）：

### 同批：vkmark 選到 `R16G16B16A16_UNORM` 後 segfault

surface 宣告 `R16G16B16A16_UNORM` 可用，但 VirtGpu 資源路徑只認 `FLOAT`，回 `VK_ERROR_FORMAT_NOT_SUPPORTED`（**guest 端的錯誤返回是乾淨的，segfault 是 vkmark 自己沒檢查回傳值**）。

**根因就是上面的 (2)**：舊樹的 strip 把這個格式從 surface 清單裡拿掉了，vkmark 根本挑不到它；新樹沒 strip，它又出現在清單裡。舊 .so 實測 1345 分佐證。補回 strip 即解，不需要往 gfxstream 的格式表補 `R16G16B16A16`。

順帶記一筆上游既有瑕疵（不在本次範圍，未動）：guest `getVirglFormat()` 把 `VK_FORMAT_A2R10G10B10_UNORM_PACK32` 對到 `VIRGL_FORMAT_R10G10B10A2_UNORM`，通道順序其實對不上。

### 真正的決定：兩個世界選一個

盤點完之後，這不是一份「補漏清單」，是一個選擇：

**世界 A（舊樹）**：host 藏 modifier extension → guest 走 LINEAR 模擬 → host 需要 B 那整組接住它。代價是要在生成檔上長期維護 patch。

**世界 B（上游／新樹）**：host 照上游暴露 modifier extension → guest 走真協商。上游是**刻意**這樣設計的，`vk_decoder_global_state.cpp:10810` 的註解明說「Mesa WSI (in Linux) 就是這樣用的」，所以 host device 上永遠 force-enable 它。代價是目前 R↔B 在這個世界裡。

支持 B 的證據：實測 kwin 的三顆 fb 是 `modifier=0x0`（LINEAR），**舊註解預言的「兩個集合不相交、協商失敗」的災難沒有發生**。發生的是更安靜的東西——雙方在「用哪個 format」上的偏好順序變了。

支持 A 的疑慮：上游驗證的 host driver 不是 Adreno。那份「只有 QCOM-tiled、只給 BGRA8、且拒絕 COLOR_ATTACHMENT」的 modifier 清單是這個硬體特有的。

**這個決定要由實驗結果拍板，不是由「舊樹本來就這樣」拍板。** 目標是最小化與上游的分歧；世界 A 的代價（生成檔 patch）很高，只有在世界 B 真的不可行時才值得。

### 驗收方法上值得留著的東西

- **gfxstream 的 log 在 Android 上進 logcat（tag `GFXSTREAM`），不是 crosvm stderr。** 舊樹註解說「crosvm 把 log level 拉高所以 warning/error 都不見」很可能是誤判 —— 訊息一直都在 logcat，只是沒人往那裡看，那批改用 raw `fprintf` 的診斷程式碼理由有一半建立在這個誤判上
- **crosvm stderr log 跨開機累積不截斷** —— 對整個檔案 grep 會把一整天所有 boot 混在一起數
- **換 `.so` 對照法**：把舊 `.so` 蓋上去跑一格再換回來，不用重編、一次開機、單一變因。`/data/local/tmp/{old,new}_backend.so` 留在 5567 上
- **`environment_variables` 欄位**（`setkeys.py`）可以直接給 crosvm 下任何 gfxstream 環境變數，不用改 app
- **「診斷沒印出來」不是證據，除非先證明那條診斷落在會被執行的路徑上。** 這一輪踩了三次：第一次把診斷放進 `VirtioGpuResource::Create` 的 `createArgs` 分支（桌面根本不走），第二次用 per-format 去重把真正的資源和 64×64 探針收斂成同一行，第三次據此推論「畫素不經過 gfxstream」。先印一行無條件的「我到這裡了」，再談有沒有印出目標
- **開診斷會改變被觀測的對象。** `GPU_SCANOUT_TRACE=1` 一開，桌面就切到 zero-copy 路徑，而 byte probe 根本不在那條路上 —— 量到的不是原本要量的東西。加觀測點前先問：這個開關會不會換掉資料路徑
- **挑測試的準則：問「兩個假設會給出不同答案」的那個問題。** 「跑純紅的 GL 程式看變不變藍」沒有鑑別力——R↔B 是對整個 framebuffer 做的，紅變藍在「zink 的問題」和「kwin 挑格式的問題」兩個假設下都會發生。換成「同一個測量、只換 `.so`，看標籤變了還是內容變了」就一次砍掉一半
- **對照組不是可選的。** 「新 .so 的位元組是 BGRA、宣告是 RGBA，所以有人翻轉了畫素」——這個推論錯了，錯在只有單一觀測。舊 .so 一跑，位元組逐 byte 相同，「翻轉」根本不存在
